# تعيين ضوابط HIPAA إلى منصة Smart Hospital

> **تنبيه قانوني:** هذا المستند تعيين هندسي وليس شهادة امتثال. لا يمكن لأي برنامج أن يجعل المنشأة "متوافقة مع HIPAA" بمفرده. الامتثال يتحقق عندما تجتمع الضوابط التقنية الموضحة هنا مع سياسات إدارية موثقة، وتدريب الموظفين، وضوابط فيزيائية، وتحليل مخاطر رسمي، وعقود BAA مع كل معالج/مزود فرعي. البنود المعلّمة بـ **مؤسسي** لا يمكن تنفيذها بالكود.

## 1. نطاق النظام

| العنصر | التفصيل |
|---|---|
| التطبيق | Jakarta EE 10، GlassFish 7.0.23، واجهة React أحادية الصفحة |
| قاعدة البيانات | MySQL 8، مخطط `hospital` |
| المصادقة | جلسات Bearer معتمة (opaque) مخزنة كتجزئة SHA-256 في `user_sessions` + مصادقة ثنائية TOTP (RFC 6238) |
| كلمات المرور | PBKDF2-HMAC-SHA256، 210,000 تكرار، ملح 16 بايت، مقارنة ثابتة الزمن |
| التدقيق | سلسلة تجزئة SHA-256 مع قفل صف `audit_chain_state` ومشغلات منع التعديل/الحذف |
| البيانات | بيانات مرضى ووصفات وفواتير ومخزون — تشمل PHI |

| البند | المتطلب | ما يلزم مؤسسياً |

## 4. الضوابط التقنية — 45 CFR §164.312

### 4.1 التحكم في الوصول — 312(a)(1)

- **مُنفّذ:** كل مسار API محمي بـ `@RequiresRoles` مخصص يُفرض داخل `AuthContextFilter`. لا توجد مصادقة حاوية BASIC.
- **مُنفّذ:** جلسات معتمة، انتهاء خمول 30 دقيقة وانتهاء مطلق 8 ساعات، إبطال جماعي عند تغيير كلمة المرور.
- **مُنفّذ:** قفل الحساب بعد 5 محاولات فاشلة لمدة 15 دقيقة، مع تسجيل `LOGIN_FAILED` في التدقيق.
- **مُنفّذ:** وصول المريض مقيّد بفرع المستخدم عبر `patient_branch_access` و`requirePatientAccess`.
- **مؤسسي:** مراجعة صلاحيات ربع سنوية (Access Review) وإزالة الحسابات غير النشطة.

### 4.2 التحقق من الهوية — 312(d)

- **مُنفّذ:** كلمات مرور بحد أدنى 12 حرفاً مع أحرف كبيرة/صغيرة/رقم/رمز، وPBKDF2.
- **مُنفّذ:** `mustChangePassword` للحسابات التجريبية والحسابات الجديدة.
- **مُنفّذ (خيار إنتاجي):** عند تفعيل `smarthospital.security.enforcePasswordRotation`، يُحجب الحساب عن كل المسارات عدا تغيير كلمة المرور/الخروج/الهوية حتى تُحدَّث كلمة المرور.
- **مُنفّذ:** مقارنة ثابتة الزمن لمنع هجمات التوقيت.
- **مُنفّذ:** مصادقة ثنائية TOTP (RFC 6238) مع خطوة تحقق ثانية، رموز استرداد لمرة واحدة، تشفير السر بـAES-256-GCM، ومنع إعادة استخدام الرمز.
- **مُنفّذ:** إلزام MFA حسب الدور عبر `smarthospital.mfa.requiredRoles` (افتراضياً غير ملزم؛ يوصى بإلزام المسؤولين والأطباء في الإنتاج).
- **مُنفّذ:** إعادة تعيين إدارية موثقة (`PATCH /admin/accounts/{id}/mfa-reset`) بعد تحقق خارج النظام، مع إبطال كل الجلسات وتدقيق `HOSPITAL_ACCOUNT_MFA_RESET`.
- **مؤسسي:** توزيع الأجهزة، حفظ رموز الاسترداد، وتدريب الموظفين (راجع `docs/MFA_RUNBOOK_AR.md`).

### 4.3 سجل التدقيق — 312(b)

- **مُنفّذ:** كل عملية حساسة تكتب `audit_logs` مع الفاعل والفرع والنتيجة وعنوان IP ووكيل المستخدم.
- **مُنفّذ:** سلسلة تجزئة SHA-256: `row_hash = SHA256(prev_hash|id|actor|branch|action|resource|outcome|occurred_at|metadata)`، والحمولة الدقيقة محفوظة في `hash_payload` (V019) للتحقق المستقل.
- **مُنفّذ:** قفل `audit_chain_state FOR UPDATE` يمنع تفرّع السلسلة؛ مشغلات تمنع UPDATE/DELETE.
- **مُنفّذ:** التحقق عبر `GET /api/v1/audit-logs/integrity` أو `scripts/verify-audit-chain.ps1`.
- **مؤسسي:** الاحتفاظ بالسجلات 6 سنوات (§164.316(b)(2)(i)) وأرشفتها WORM/immutable.

### 4.4 سلامة البيانات — 312(c)

- **مُنفّذ:** قيود CHECK على قيم الحساسية/التحقق/الموافقات، ومفاتيح أجنبية، و`@Version` (قفل تفاؤلي) على الكيانات الأساسية.
- **مُنفّذ:** فحص الحساسية والتفاعلات الدوائية قبل الكتابة، مع منع الوصفات الخطرة إلا بمبرر سريري موثق ومُدقّق.
- **مُنفّذ:** سلسلة تدقيق تكشف أي تعديل لاحق على السجلات.
- **مؤسسي:** مراجعة دورية لتكامل البيانات ومطابقة الوصفات مع السجل السريري.

### 4.5 نقل البيانات — 312(e)(1)

- **مُنفّذ:** رؤوس أمان (`HSTS` عند HTTPS، `CSP`, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`).
- **مُنفّذ:** إعادة توجيه HTTPS اختيارية عبر `-Dsmarthospital.forceHttps=true` أو `SMART_HOSPITAL_FORCE_HTTPS=true`.
- **مؤسسي/بنية تحتية:** شهادة TLS صالحة من CA موثوق (وليس self-signed)، TLS 1.2+ فقط، وإنهاء TLS على موازن موثوق.
- **مؤسسي:** تشفير الأقراص/النسخ الاحتياطية At Rest (BitLocker/LUKS أو تشفير MySQL).

## 5. قاعدة الخصوصية — 45 CFR §164.500–534

| المتطلب | الدعم في النظام | مؤسسي |
|---|---|---|
| الحد الأدنى الضروري | أدوار دقيقة + نطاق فروع + عدم كشف PHI في مقاييس الأمان | مراجعة الحاجة للمعلومة لكل دور |
| حق الوصول للفرد | سجل زيارات/وصفات قابل للتصدير | إجراءات طلب ونسخ السجلات |
| تصحيح المعلومات | واجهات تعديل المرضى + سجل تدقيق | التحقق من الطلبات وتوثيق الرفض |
| محاسبة الإفصاحات | `audit_logs` تسجل من فعل ماذا ومتى | تصنيف الإفصاحات وتقارير سنوية |
| الموافقات | `patient_consents` (منح/سحب) + تدقيق | نماذج موافقة موقعة ومحفوظة |
| الحد الأدنى للاستخدام | لا تُعاد بيانات PHI في `/security/metrics` | سياسة استخدام مقبول |

## 6. إشعار خرق البيانات — 45 CFR §164.400–414

- **مُنفّذ تقنياً:** سلسلة تدقيق تكشف التلاعب، وتسجيل محاولات الدخول الفاشلة، وإمكانية تصدير السجلات.
- **مؤسسي:** تقييم الخرق خلال 60 يوماً، إشعار الأفراد/HHS/الإعلام حسب الحجم، وتوثيق كامل. راجع `docs/INCIDENT_RESPONSE_AR.md`.

## 7. الفجوات المعروفة قبل الإنتاج التجاري

1. **تفعيل سياسة إلزام MFA** — المنصة تدعمها بالكامل؛ يلزم قرار تشغيلي بتحديد الأدوار الملزمة وتسجيل جميع مستخدميها (`smarthospital.mfa.requiredRoles`).
2. **TLS بشهادة موثوقة** — الشهادة الحالية self-signed للتطوير فقط.
3. **تشفير At Rest** — يعتمد على البنية التحتية؛ يجب توثيقه وإثباته.
4. **إدارة الأسرار** — كلمة مرور MySQL ومفتاح التوقيع يجب أن تُدار عبر خزنة أسرار (Vault/KMS)، لا ملفات محلية.
5. **مراجعة الكود الأمني المستقل** واختبار اختراق قبل الإطلاق التجاري.
6. **BAA** مع مزود الاستضافة وأي معالج فرعي.
7. **الاحتفاظ 6 سنوات** لأرشيف التدقيق مع ضمان عدم القابلية للتعديل.
8. **التوطين والخصوصية المحلية** — راجع قوانين حماية البيانات في بلد التشغيل (مثل PDPL) إضافة إلى HIPAA عند التعامل مع بيانات أمريكية.

## 8. أدلة التحقق المقترحة عند التدقيق

- لقطة من `GET /api/v1/audit-logs/integrity` تظهر `chainIntact=true`.
- مخرجات `scripts/smoke-test.ps1` بنجاح كامل (56 فحصاً).
- سجل `schema_version` يظهر V001–V022.
- نتيجة `mvn clean verify` مع 39 اختبار وحدة ناجح.
- نتائج اختبار MFA: تسجيل، تحقق، رفض رمز خاطئ/معاد استخدامه، رمز استرداد، إعادة تعيين إدارية، وإبطال الجلسات.
- نسخة احتياطية مع ملف `.sha256` واستعادة ناجحة إلى قاعدة منفصلة.
- سياسات موقعة: الأمن، الحوادث، النسخ الاحتياطي، تدريب الموظفين.
