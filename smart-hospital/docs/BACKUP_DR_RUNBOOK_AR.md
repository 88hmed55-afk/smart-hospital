# دليل النسخ الاحتياطي والاستعادة والتعافي من الكوارث — Smart Hospital

## 1. الأهداف
| المقياس | الهدف |
|---|---|
| RPO (أقصى فقدان بيانات مقبول) | ≤ 15 دقيقة (مع binlog) أو ≤ 24 ساعة (نسخ يومية فقط) |
| RTO (أقصى زمن تعافٍ) | ≤ 4 ساعات |
| فترة الاحتفاظ اليومية | 14 يوماً |
| الاحتفاظ الشهري | 12 شهراً |
| سجلات التدقيق/المالية | 6 سنوات (أرشيف غير قابل للتعديل) |

## 2. النسخ الاحتياطي

### 2.1 النسخة اليومية الكاملة
```powershell
cd smart-hospital
.\scripts\backup-database.ps1 `
  -LoginPath smart-hospital-local `
  -BackupDirectory 'D:\backups\smart-hospital' `
  -RetentionDays 14
```
ينتج:
- `hospital-YYYYMMDD-HHmmss.sql` — نسخة منطقية متسقة (single-transaction).
- `....sql.sha256` — بصمة للتحقق قبل الاستعادة.
- طباعة `BACKUP_OK` عند النجاح (استخدمها في المراقبة).

### 2.2 جدولة يومية (Task Scheduler)
```powershell
$action = New-ScheduledTaskAction -Execute 'powershell.exe' `
  -Argument '-ExecutionPolicy Bypass -File "C:\path\smart-hospital\scripts\backup-database.ps1" -BackupDirectory "D:\backups\smart-hospital"'
$trigger = New-ScheduledTaskTrigger -Daily -At 2:00AM
Register-ScheduledTask -TaskName 'SmartHospital-Backup' -Action $action -Trigger $trigger -RunLevel Highest
```

### 2.3 نسخ ساعية (موصى به)
فعّل MySQL binary log واحتفظ بنسخه كل 15 دقيقة:
```sql
-- my.ini: log_bin = mysql-bin ; expire_logs_days = 7
FLUSH BINARY LOGS;
```
انسخ ملفات `mysql-bin.*` إلى تخزين منفصل مشفّر.

### 2.4 ضوابط التخزين
- تشفير النسخ (BitLocker/LUKS أو أداة أرشفة مشفرة).
- تخزين خارج الخادم (NAS/كائن سحابي) مع مصادقة منفصلة.
- منع وصول تطبيق الإنتاج إلى مجلد النسخ.
- اختبار قابلية القراءة أسبوعياً.

### 2.5 مفتاح المصادقة الثنائية (MFA Key)
- مفتاح AES-256-GCM لتشفير أسرار TOTP **ليس داخل قاعدة البيانات**. فقدانه يعني إعادة تسجيل MFA لكل الحسابات.
- وفّره عبر `SMART_HOSPITAL_MFA_KEY` أو `-Dsmarthospital.mfa.key` (Base64 لـ32 بايت)، أو ملف `~/.smart-hospital/mfa.key` للتطوير فقط.
- احتفظ بنسخة منه في خزنة أسرار منفصلة عن نسخ قاعدة البيانات، مع وصول مقيّد لمسؤولين اثنين على الأقل.
- **لا تُدرجه داخل ملف النسخة الاحتياطية لقاعدة البيانات**؛ بل وثّق موقعه وإجراء استعادته في خطة DR.
- عند الاستعادة إلى خادم جديد: وفّر المفتاح أولاً ثم شغّل التطبيق، ثم تحقق من تسجيل دخول حساب MFA فعلي.
- تدوير المفتاح يبطل كل الأسرار الحالية؛ يتطلب نافذة صيانة وإعادة تسجيل جماعية.
- التفاصيل في `docs/MFA_RUNBOOK_AR.md`.

## 3. الاستعادة

### 3.1 استعادة إلى قاعدة اختبار (الافتراضي الآمن)
```powershell
.\scripts\restore-database.ps1 -BackupFile 'D:\backups\smart-hospital\hospital-20261110-020000.sql'
```
يُنشئ `hospital_restore_<timestamp>` ويتحقق من:
- تطابق SHA-256،
- وجود `CREATE TABLE` و`schema_version`،
- عدد الجداول ≥ 10.

### 3.2 استعادة فوق قاعدة الإنتاج (طوارئ فقط)
```powershell
.\scripts\restore-database.ps1 `
  -BackupFile '...\hospital-....sql' `
  -TargetDatabase hospital `
  -AllowOverwrite -DropAndRecreate `
  -ConfirmToken 'RESTORE hospital'
```
> لا تنفّذ هذا دون موافقة مالك النظام، وبعد أخذ نسخة من الوضع الحالي إن أمكن.

### 3.3 التحقق بعد الاستعادة
1. `.\scripts\verify-audit-chain.ps1` — يجب `AUDIT_CHAIN_OK`.
2. `.\scripts\smoke-test.ps1` — يجب نجاح 56 فحصاً.
3. أعد تشغيل التطبيق إن تغيّر اتصال قاعدة البيانات.
4. راجع `security/metrics` للتأكد من الجلسات والحسابات.

## 4. التعافي من الكوارث (DR)

### 4.1 ترتيب الاستعادة
1. البنية التحتية (الخادم/الشبكة).
2. MySQL من آخر نسخة + binlog.
3. **مفتاح MFA** (متغير بيئة/خزنة أسرار) قبل تشغيل التطبيق، ثم تطبيق GlassFish وEAR.
4. شهادة TLS والإعدادات.
5. التحقق من سلسلة التدقيق واختبار الدخان.
6. إشعار المستخدمين بعودة الخدمة.

### 4.2 سيناريوهات
| السيناريو | الإجراء |
|---|---|
| تلف قاعدة البيانات | استعادة آخر نسخة + binlog إلى لحظة الحادث |
| فقدان الخادم | تجهيز خادم بديل بنفس الإصدارات واستعادة الملفات |
| فدية/تشفير | عزل، استعادة من نسخة سليمة، تحقق من عدم وجود باب خلفي |
| حذف بيانات بالخطأ | استعادة انتقائية إلى قاعدة منفصلة ثم نقل الجداول المطلوبة |
| انقطاع مركز بيانات | التحول للموقع البديل (إن وجد) |

### 4.3 اختبار دوري
- شهرياً: استعادة نسخة إلى قاعدة اختبار + smoke test.
- ربع سنوياً: تمرين DR كامل مع وقت قياس.
- توثيق النتائج والزمن الفعلي وخطط التحسين.
