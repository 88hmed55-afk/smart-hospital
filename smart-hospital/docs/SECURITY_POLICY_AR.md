# سياسة أمن المعلومات — Smart Hospital

> نسخة قابلة للاعتماد: عدّل الحقول بين `[...]`، واعتمدها من الإدارة العليا، وأعد مراجعتها سنوياً.

## 1. الغرض والنطاق
تحمي هذه السياسة سرية وسلامة وتوافر معلومات المرضى (PHI) والبيانات المالية والتشغيلية في منصة Smart Hospital، وتنطبق على كل موظف ومتعاقد ومزود يصل إلى النظام أو بياناته.

## 2. الأدوار والمسؤوليات

| الدور | المسؤولية |
|---|---|
| مالك النظام (System Owner) | اعتماد التغييرات والمخاطر المتبقية |
| مسؤول أمن المعلومات (ISO) | تطبيق السياسة، مراجعة السجلات، إدارة الحوادث |
| مسؤول قاعدة البيانات (DBA) | النسخ الاحتياطي، الاستعادة، مراجعة الصلاحيات |
| مسؤول الخادم | الترقيع، TLS، السجلات، المراقبة |
| مدير الموارد البشرية | التعيين/النقل/الإنهاء، تدريب الموظفين |
| جميع المستخدمين | الالتزام، الإبلاغ عن الحوادث فوراً |

## 3. إدارة الهوية والوصول
1. الوصول يُمنح وفق مبدأ الحد الأدنى الضروري وبموافقة مدير مباشر.
2. كل مستخدم يملك حساباً شخصياً؛ يُمنع الحسابات المشتركة.
3. الأدوار المتاحة: `HOSPITAL_ADMIN`, `HOSPITAL_MANAGER`, `RECEPTIONIST`, `DOCTOR`, `NURSE`, `LAB_TECHNICIAN`, `LAB_SUPERVISOR`, `PHARMACIST`, `ACCOUNTANT`, `INVENTORY_OFFICER`.
4. الوصول لبيانات المريض يتطلب ارتباط المستخدم بفرع المريض (`user_branch_access` + `patient_branch_access`).
5. عند إنهاء الخدمة: تعطيل الحساب فوراً، إبطال كل الجلسات، واسترداد الأجهزة.
6. مراجعة صلاحيات ربع سنوية موثقة، وإزالة الحسابات الخاملة أكثر من 90 يوماً.
7. إنشاء الحسابات يتم من واجهة الإدارة بكلمة مرور أولية قوية تحمل `must_change_password=TRUE`، وتُسلَّم للموظف بقناة موثوقة.

## 4. كلمات المرور والمصادقة
- الحد الأدنى 12 حرفاً، تشمل حرفاً كبيراً وصغيراً ورقماً ورمزاً.
- تُخزَّن كلمات المرور بـ PBKDF2-HMAC-SHA256 (210,000 تكرار) ولا تُسجَّل أو تُرسل عبر البريد.
- قفل الحساب بعد 5 محاولات فاشلة لمدة 15 دقيقة.
- انتهاء الجلسة بعد 30 دقيقة خمول أو 8 ساعات كحد أقصى.
- يُمنع تشارك بيانات الدخول أو كتابتها في ملفات/سكربتات.
- تُفرض المصادقة الثنائية (TOTP) على الأدوار الحساسة في الإنتاج، ويُوثّق قرار الأدوار الملزمة.

### 4.1 المصادقة الثنائية (MFA)
- TOTP وفق RFC 6238: SHA-1، 6 أرقام، 30 ثانية، نافذة ±1، ومنع إعادة استخدام الرمز.
- الأسرار مشفّرة بـAES-256-GCM؛ المفتاح يُدار عبر خزنة أسرار/متغير بيئة ويُنسخ احتياطياً منفصلاً عن قاعدة البيانات.
- يُمنع تعطيل MFA أو إعادة إنشاء رموز الاسترداد دون كلمة المرور ورمز صالح؛ التعطيل يُبطل كل الجلسات.
- إلزام الأدوار عبر `smarthospital.mfa.requiredRoles`؛ الافتراضي غير ملزم، ويجب تفعيله للمسؤولين والأطباء قبل الإنتاج.
- إعادة تعيين عامل ثانٍ مفقود تتم فقط بعد تحقق خارج النظام، بموجب سبب موثق، من مسؤول آخر (لا يمكن للمسؤول إعادة تعيين نفسه)، مع إبطال الجلسات وتدقيق الإجراء.
- 10 رموز استرداد لمرة واحدة لكل حساب، تُخزَّن كتجزئة وتُسلَّم للموظف بأمان.
- تفاصيل التشغيل: `docs/MFA_RUNBOOK_AR.md`.

## 5. حماية البيانات
1. تصنيف البيانات: PHI، مالية، تشغيلية، عامة.
2. PHI لا تُنسخ إلى أجهزة محمولة أو بريد شخصي.
3. الاتصال بالإنتاج عبر HTTPS فقط؛ شهادة من CA موثوق.
4. تشفير الأقراص والنسخ الاحتياطية (BitLocker/LUKS أو ما يعادله).
5. عدم استخدام بيانات إنتاج حقيقية في بيئة الاختبار؛ استخدم بيانات مُجهّلة.

## 6. سجل التدقيق والمراقبة
- كل وصول/تعديل حساس يُسجَّل في `audit_logs` بسلسلة تجزئة قابلة للتحقق.
- التحقق اليومي الآلي عبر `GET /api/v1/audit-logs/integrity`.
- مراجعة أسبوعية لمؤشرات `/api/v1/security/metrics`: الجلسات النشطة، الحسابات المقفلة، فشل الدخول، حالة MFA (`mfaEnabledAccounts`, `accountsPendingMfaEnrollment`, `mfaFailures24h`)، وسلامة السلسلة.
- تنبيه فوري عند `auditChainIntact=false` أو تجاوز فشل الدخول حداً غير طبيعي.
- الاحتفاظ بالسجلات 6 سنوات في وسيط غير قابل للتعديل.

## 7. النسخ الاحتياطي والاستعادة
- نسخة كاملة يومية + نسخ ساعية للـ binlog إن أمكن.
- تشفير النسخ، والتحقق من `.sha256` قبل كل استعادة.
- اختبار استعادة شهري إلى قاعدة منفصلة.
- الاحتفاظ: 14 يوماً يومياً، 12 شهراً شهرياً، 6 سنوات للسجلات المالية/التدقيق حسب السياسة.

## 8. إدارة التغيير
- لا نشر مباشر على الإنتاج دون مراجعة كود واختبارات ناجحة.
- كل تغيير قاعدة بيانات يُنفَّذ عبر ترحيل مرقّم (`V0xx`) ومسجل في `schema_version`.
- خطة تراجع (Rollback) موثقة قبل كل نشر.
