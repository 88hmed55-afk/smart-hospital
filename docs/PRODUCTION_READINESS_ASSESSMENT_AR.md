# تقييم جاهزية Smart Hospital للإنتاج والاستخدام مع بيانات مرضى حقيقية

**تاريخ التقييم:** 2026-11-09
**الإصدار المقيَّم:** 1.0.0
**بيئة التقييم:** Windows + JDK 17.0.12 + GlassFish 7.0.23 + MySQL 8.0.38 + Jakarta EE 10
**منهجية التقييم:** فحص كود المصدر + فحص قاعدة البيانات الحيّة + اختبار نقاط النهاية الحيّة + مقارنة بمعايير مرجعية منشورة

## 2. ما تم التحقق منه فعلياً (وليس افتراضاً)

### 2.1 التطبيق يعمل
- `http://localhost:8080/` → **200**، وتحميل SPA يعمل.
- `https://localhost:8181/` → **200** بشهادة ذاتية التوقيع (`s1as`).
- `GET /api/v1/security/me` بمستخدم `hospitaladmin` → **200** مع `roleCodes`, `branchIds`, `defaultBranchId`.
- اختبار الدخان الآلي: **30/30 ناجح** (SPA + صحة + وحدات + منع الأدوار).
- تطبيق واحد فقط منشور: `smart-hospital <ear, ejb, web>`.

### 2.2 التحكم بالوصول
- **93/93** نقطة نهاية HTTP موجودة داخل أصناف تحمل `@RolesAllowed`.
- `web.xml` يفرض BASIC auth على `/api/v1/*` لكل الأدوار العشرة.
- `CurrentUserService` يربط هوية GlassFish بحساب DB نشط + فروع + أدوار، ويرفض الحساب غير الموجود/المعطّل.
- اختبارات منع الأدوار ناجحة: طبيب → إدارة = 403، ممرض → فواتير = 403، محاسب → إدارة = 403.

### 2.3 قاعدة البيانات
- **64 جدولاً**، مفاتيح أجنبية، قيود `CHECK`، فهارس، مشغّلات UUID.
- **175** تعليق Bean Validation في الـ DTOs (تحقق مدخلات جيد نسبياً).
- بيانات تجريبية: مريض واحد، **0** زيارة/موعد/تنويم/فاتورة/وصفة/طلب مختبر، **44** سجل تدقيق.
- كتالوج التشخيص: `DEMO / TEST-DIAG-001..003`. كتالوج المختبر: `DEMO-LAB-CBC`, `DEMO-LAB-GLU` مع `DEMO-SPECIMEN`.

### 2.4 التدقيق (Audit)
- **26** استدعاء تدقيق موزّعة على **13** خدمة (ClinicalService 11، Procurement 7، Accounting 6، Laboratory 5، …).
- لكن: لا تدقيق لتسجيل الدخول/الخروج، ولا تعبئة لـ `ip_address` / `user_agent`، ولا منع تعديل/حذف حقيقي (V011 يضيف فهرساً فقط)، ولا سلسلة تجزئة (hash chain)، ومستخدم التطبيق يملك `UPDATE/DELETE` على `audit_logs`.

### 2.5 الفجوات المؤكدة بالفحص (لا بالانطباع)

| المجال | الفجوة المؤكدة |
|--------|----------------|
| رؤوس الأمان | لا يوجد `Content-Security-Policy`، `X-Frame-Options`، `Strict-Transport-Security`، `X-Content-Type-Options`، `Referrer-Policy` (فُحصت رؤوس الاستجابة فعلياً). |
| النقل | `web.xml` بلا `transport-guarantee=CONFIDENTIAL`؛ التطبيق يعمل على 8080 HTTP بلا تحويل إلى 8181، ولا HSTS. |
| المصادقة | File Realm، كلمة مرور موحّدة `Demo@2026` لكل الحسابات، لا قفل حساب، لا حد لمحاولات الدخول، لا سياسة كلمات مرور، لا دورة تصفير/تغيير كلمة مرور (يوجد حقل `mustChangePassword` لكن بلا تنفيذ فعلي). |
| الجلسات | BASIC auth بلا مهلة جلسة صريحة مضبوطة، والتوكن يُحفظ في الذاكرة فقط. |
| قاعدة البيانات | `sslMode=DISABLED`، كلمة مرور DB مكتوبة في الوثائق، مستخدم التطبيق يملك حذف/تعديل على جداول التدقيق. |
| التكامل | **صفر** ذكر لـ FHIR / HL7 / DICOM / ICD-10 / SNOMED / LOINC / ATC في الكود أو المخطط. |
| الجودة | لا JUnit، لا Arquillian، لا CI/CD، لا مستودع Git، لا اختبارات تحميل/أمان. |
| ترقيات المخطط | لا Flyway / Liquibase / جدول `schema_version`؛ الترقيات سكربتات يدوية. |
| الاعتمادية | لا نسخ احتياطي آلي، لا استعادة، لا DR، لا مراقبة/تنبيهات تتجاوز `/health` و`/health/ready`. |
| التزامن | `@Version` على كيان واحد فقط من عشرات الكيانات → خطر Lost Updates. |
| السلامة الدوائية | `PharmacyService` لا يفحص الحساسية ولا التفاعلات الدوائية ولا الجرعة حسب الوزن/العمر. |
| هوية المريض | منع التكرار يعتمد على `MRN` فقط؛ لا تحقق من الهوية الوطنية ولا تشابه الاسم+تاريخ الميلاد. |
| الطباعة/التقارير | لا PDF، لا CSV، لا `@media print`، لا طباعة فاتورة/وصفة/تقرير مخبري. |
| الوصولية | عنصر `aria-label` واحد فقط في الواجهة كلها؛ لا مراجعة WCAG. |
| الخصوصية | لا موافقة مستنيرة (Consent)، لا تصحيح/حذف بيانات، لا تصنيف حساسية للحقول، لا إخفاء للبيانات في السجلات. |
| الحوكمة | لا `LICENSE`، لا سياسة أمن معلومات، لا DPA، لا تقييم مخاطر. |
| توثيق الخطة | `docs/06-ROADMAP.md` يصف PostgreSQL وFlyway وArgon2 و`AuthService` وCSRF — وهو **مخالف للمنفَّذ فعلياً** (MySQL، File Realm، BASIC، SQL خام). |

### 2.6 نقاط قوة حقيقية
- فصل طبقات نظيف (Resource → Service → Entity/DTO) واتساق تسمية جيد.
- تدقيق داخل نفس معاملة JTA للعمليات الحساسة (قرار صحيح).
- قفل متشائم (pessimistic lock) على صف الزيارة في العمليات المتزامنة.
- Idempotency للمدفوعات (`idempotency_key` + `request_fingerprint`).
- SPA fallback سليم، وواجهة عربية RTL، واستخدام `Intl` في 27 موضعاً.
- `dangerouslySetInnerHTML` = 0، و`npm audit --omit=dev` = **0 ثغرات**.
- تعليقات الأخطاء التجارية برموز واضحة بدل رسائل مبهمة.

## 5. الفجوات الحرجة (Blockers) — لا تُتجاوز قبل أي مريض حقيقي

1. **فرض TLS:** إعادة توجيه 8080→8181، إضافة `transport-guarantee=CONFIDENTIAL`، تفعيل HSTS، وتشغيل MySQL بـ `sslMode=VERIFY_CA`.
2. **استبدال File Realm بمصادقة تطبيقية:** جدول مستخدمين بكلمات مرور مُجزّأة (Argon2id/bcrypt)، سياسة كلمات مرور، قفل تدريجي، MFA للأدوار الحساسة، وتدقيق دخول/خروج.
3. **إدارة أسرار حقيقية:** إخراج كلمة مرور DB من الوثائق، تدويرها، واستخدام مخزن أسرار/متغيرات بيئة.
4. **تدقيق غير قابل للتعديل:** منع `UPDATE/DELETE` على `audit_logs` (صلاحيات DB أو triggers)، تعبئة IP/User-Agent، سلسلة تجزئة، وسياسة احتفاظ.
5. **رؤوس أمان + CSP:** إضافة فلتر يعيّن CSP وX-Frame-Options وX-Content-Type-Options وReferrer-Policy وPermissions-Policy.
6. **نسخ احتياطي واستعادة مُختبرة:** نسخ يومي + PITR، وتوثيق RPO/RTO، واختبار استعادة فعلي.
7. **إدارة الترقيات:** Flyway أو Liquibase + جدول إصدار + منع أي تعديل يدوي على الإنتاج.
8. **اختبارات وCI:** JUnit + اختبارات تكامل + فحص أمني آلي + بوابة بناء.
9. **منع Lost Updates:** إضافة `@Version` لكل الكيانات القابلة للتعديل.
10. **سلامة دوائية أساسية:** فحص حساسية المريض وتفاعلات دوائية وحدود الجرعة قبل حفظ الوصفة.

## 6. الخطة العلاجية

### المرحلة 1 — «قبل أي بيانات حقيقية» (4–6 أسابيع)
- TLS إجباري + HSTS + TLS لقاعدة البيانات.
- مصادقة تطبيقية كاملة + قفل + تدقيق دخول.
- رؤوس أمان + CSP.
- منع تعديل `audit_logs` + IP/User-Agent + hash chain.
- Flyway + `@Version` لكل الكيانات.
- نسخ احتياطي آلي + اختبار استعادة موثّق.
- إخراج الأسرار من الوثائق + استبدال كلمة المرور الموحّدة.

### المرحلة 2 — «قابل للتشغيل في مستشفى واحد» (2–3 أشهر)
- JUnit + اختبارات تكامل + CI.
- فحص حساسية/تفاعلات/جرعات.
- طباعة PDF للفاتورة والوصفة والتقرير المخبري.
- Consent + تصنيف حساسية الحقول + إخفاء البيانات في السجلات.
- مراقبة وتنبيهات (DB، JVM، أخطاء، أمن).
- تقييم مخاطر + خطة استجابة للحوادث + سياسات مكتوبة.
- إصلاح تضارب وثائق الخطة مع الواقع.

### المرحلة 3 — «قابل للاعتماد والتكامل» (3–6 أشهر)
- ICD-10 + LOINC + SNOMED (على الأقل مجموعات فرعية).
- HL7 FHIR R5 (Patient, Encounter, Observation, MedicationRequest, DiagnosticReport).
- HL7 v2 ADT/ORM للربط مع الأنظمة القائمة.
- DICOM/PACS للأشعة.
- إدارة هوية المريض (EMPI) ومطابقة السجلات.
- بوابة مريض + موافقة إلكترونية.
- اختبار اختراق مستقل + مراجعة امتثال.

## 7. قائمة التحقق قبل أول مريض حقيقي

- [ ] TLS إجباري على كل المسارات، وشهادة من CA موثوقة.
- [ ] قاعدة بيانات على TLS، ومستخدم مبدأ الامتياز الأدنى فقط.
- [ ] كلمات مرور مُجزّأة وسياسة وقفل حساب وMFA للأدوار الحساسة.
- [ ] لا أسرار في المستودع أو الوثائق.
- [ ] `audit_logs` غير قابل للتعديل، مع IP/User-Agent وسلسلة تجزئة.
- [ ] نسخ احتياطي يومي + استعادة مُختبرة + RPO/RTO معلنة.
- [ ] Flyway/Liquibase يملك المخطط، ولا تعديل يدوي.
- [ ] `@Version` على كل الكيانات القابلة للتعديل.
- [ ] اختبارات وحدات + تكامل + CI أخضر.
- [ ] فحص حساسية وتفاعلات دوائية وحدود جرعة.
- [ ] طباعة/تصدير للوثائق المالية والسريرية.
- [ ] Consent + سياسة خصوصية + خطة استجابة للحوادث.
- [ ] مراقبة وتنبيهات + سجلات مركزية.
- [ ] مراجعة أمنية مستقلة (Pen Test).
- [ ] مطابقة المتطلبات المحلية للجهة الصحية والجهة الرقابية.

## 8. للسوق الوظيفي — كيف تعرضه؟

**افعله:**
- قدّمه كـ **Enterprise Java + React Portfolio**: Jakarta EE 10، EAR متعدد الوحدات، GlassFish، MySQL، RBAC، JTA، تدقيق، تحليلات.
- أبرز القرارات الهندسية: فصل الطبقات، التدقيق داخل المعاملة، قفل متشائم، Idempotency للمدفوعات، SPA fallback، ضبط الأدوار.
- اذكر بصراحة ما هو **مؤجّل** ولماذا (وهذا يُحسب لك في المقابلات أكثر من الادعاء).

**لا تفعله:**
- لا تقل «جاهز للإنتاج» أو «متوافق مع HIPAA» — أي مراجع تقني سيكشف الفجوات في دقائق.
- لا تستخدم بيانات مرضى حقيقية في العرض. استخدم بيانات اصطناعية موسومة بوضوح.

**الجملة الآمنة والدقيقة:**
> «نظام مستشفى متكامل كـ MVP احترافي على Jakarta EE 10 وMySQL، بتغطية وظيفية واسعة وتحكم وصول قائم على الأدوار، ومُصمَّم للتطوير نحو جاهزية إنتاجية عبر خطة مرحلية موثّقة.»
